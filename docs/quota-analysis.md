# 免费额度预算与性能设计

目标：在 **Workers Free + D1 Free + R2 Free + Pages Free** 内运行，且不牺牲功能。

## 1. 单次操作成本（实测/推导）

| 操作 | Worker 请求 | D1 读（行） | D1 写（行） | Git 子请求 | R2 操作 |
|---|---|---|---|---|---|
| 登录 | 1 | ~2 | 2（会话 + 清理） | 0 | 0 |
| 控制台 | 1 | ~38（6 次聚合查询） | 0 | 0–1（首次建索引） | 0 |
| 文章列表 | 1 | ~35（索引 + 设置） | 0 | 0（tree 30 s 缓存） | 0 |
| 打开文章 | 1 | ~2 | 0 | 1 | 0 |
| 保存/发布文章 | 1 | ~2 | 2–4 | 1–2 | 0 |
| 删除/重命名 | 1 | ~3 | 2–4 | 1–3 | 0 |
| 配置保存 | 1 | ~2 | 1 | 1 | 0 |
| 图片上传 | 1 | ~1 | 1 | 0（R2）/1（GitHub） | 1 Class A |
| 图片访问 | 1 | 0 | 0 | 0 | 1 Class B |
| `/pub/statistic` | 1 | ~3 | 3 | 0 | 0 |
| `/pub/talks` | 1 | ~2 | 0 | 0 | 0 |

实测：整轮验收（37 个用例，覆盖约 14 次内容写操作）共触发 **36 次 Git API 调用**，即每次内容操作平均 **≈2.6 次**，低于 50 子请求上限一个数量级。

## 2. 日/月容量推算

| 资源 | Free 配额 | 折算 |
|---|---|---|
| Worker 请求 | 100,000 / 天 | 3,000 次后台浏览 + 90,000 次主题公开接口 |
| D1 行读 | 5,000,000 / 天 | 约 140,000 次文章列表（35 行/次） |
| D1 行写 | 100,000 / 天 | 约 25,000 次内容保存（4 行/次）或 33,000 次页面浏览统计（3 行/次） |
| D1 存储 | 5 GB | 索引行约 0.5 KB/篇，10 万篇仅 50 MB |
| R2 存储 | 10 GB-月 | 约 10 万张 100 KB 图片 |
| R2 Class A | 1,000,000 / 月 | 33,000 次上传/天 |
| R2 Class B | 10,000,000 / 月 | 330,000 次图片访问/天 |
| Pages 构建 | 500 / 月 | 16 次/天；批量改稿时可用 Deploy Hook 合并触发 |
| KV（可选） | 100,000 读 / 1,000 写 | 仅作冷启动缓存；默认关闭，不依赖 |

结论：对个人博客（日均 PV < 5,000、日更 1–3 篇）**余量在 10 倍以上**；瓶颈不是 Worker，而是 Pages 的 500 次/月构建。

## 3. 降低开销的 8 处设计

1. **静态资源与 API 分离**：`run_worker_first = ["/api/*","/pub/*","/webhook/*"]`，SPA、词典、CSS 由 Assets 直接返回，不消耗 Worker 请求。
2. **一次 tree 拉全量**：GitHub `GET /git/trees/{branch}?recursive=1` 替代逐目录 `contents` 遍历，列表刷新从 O(目录数) 降到 1 次。
3. **tree 快照落 D1，TTL 30 s**：连续浏览/搜索不再触网。
4. **blob sha 复用**：tree 返回的 blob sha 可直接作为 `PUT contents` 的 `sha`，更新文件从 2 次调用降为 1 次。
5. **设置内存缓存 15 s**：每个请求的配置读取从 5 次查询降为 0–1 次。
6. **写路径批量**：索引刷新、导入、统计累计使用 `DB.batch()`，一次网络往返。
7. **公开接口短缓存**：`/pub/status` 60 s D1 缓存；主题侧可再加 `Cache-Control`。
8. **密钥与解析隔离**：YAML 只在配置页解析；正文列表不解析 front-matter，避免 CPU 峰值。

## 4. CPU 10 ms 预算核对

| 路径 | 估算 CPU | 说明 |
|---|---|---|
| 文章列表 | 0.5–1.5 ms | 2 次 D1 + JSON 序列化 |
| 保存文章 | 1–2 ms | front-matter 序列化（`yaml.stringify` 小对象） |
| 配置保存 | 3–6 ms | 解析 `_config.yml`（约 3 KB）；仍在 10 ms 内，且为低频操作 |
| 登录 | 1–2 ms JS + WebCrypto PBKDF2 | PBKDF2 由 BoringSSL 原生执行，不占 JS CPU |
| 统计 | 0.5 ms | 3 条 UPSERT |
| 图片上传 | 1–3 ms | Base64/ArrayBuffer 拷贝；不转码 |

设计红线：不在请求内做「全仓库 Markdown 渲染」「图片压缩」「大文件 Base64 往返」。这三类在 Qexo 里由 Python 完成，迁移后交给构建流水线（Pages/CI）。

## 5. 与 Paid 计划的切换点

出现以下任一情况时应升级 Workers Paid（$5/月）：

- 日请求持续 > 80,000；
- 需要 CPU > 10 ms 的批量操作（如一次性导入上万篇文章）；
- 需要 > 50 子请求（批量删除大目录、全量重建索引）；
- 需要使用 Queues/Cron 做后台任务（Free 仅 5 个 Cron、10 ms CPU）。

升级不需要改代码：`wrangler.toml` 不变，仅账户计划变更；可另加 `limits.cpu_ms` 提升单请求上限。
